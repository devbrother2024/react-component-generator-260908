# commit: 변경사항 분석·분류·커밋

현재 작업 디렉토리의 git 저장소에 있는 변경사항을 분석해 논리적 단위로 나누고, 단위별 커밋 메시지를 작성해 사용자 승인 후 커밋한다. 특정 프로젝트를 가정하지 않는다 — 항상 현재 작업 디렉토리의 git 저장소를 기준으로 동작한다.

## Step 0: 사전 확인

1. `git rev-parse --is-inside-work-tree`로 현재 위치가 git 저장소인지 확인한다. 저장소가 아니면 사용자에게 알리고 종료한다.
2. `git status`로 커밋할 변경사항(staged + unstaged + untracked)이 있는지 확인한다. 아무 변경사항도 없으면 그 사실을 알리고 종료한다.
3. 저장소 루트의 `CLAUDE.md`/`AGENTS.md`/`CONTRIBUTING.md`에 커밋 메시지 컨벤션이 명시돼 있는지 확인한다. 있으면 그 규칙을 따르고, 없으면 아래 "커밋 메시지 규칙"의 기본값(Conventional Commits 스타일 + 한국어 요약)을 쓴다. `git log --oneline -20`으로 최근 커밋 메시지 스타일도 함께 확인해 — 예를 들어 이미 `feat:`, `fix:` 같은 prefix를 쓰고 있는지, 아니면 다른 스타일(이슈 번호 포함 등)을 쓰는지 — 기존 관례와 어긋나지 않게 맞춘다.

## Step 1: 변경사항 분석

- `git diff`(unstaged), `git diff --staged`(staged), `git status --porcelain`(untracked 포함)으로 전체 변경 파일과 내용을 파악한다.
- 각 파일에서 실제로 무엇이 바뀌었는지 diff 내용을 읽고 이해한다. 파일명만 보고 추측하지 않는다 — 예를 들어 파일명이 `utils.ts`라도 실제 diff 내용이 버그 수정인지 리팩터링인지는 코드를 봐야 안다.
- 이미 staged된 변경과 아직 안 된 변경이 섞여 있으면 둘 다 분석 대상에 포함한다(어차피 아래에서 단위별로 다시 add하게 된다).

## Step 2: 논리적 단위로 분류

변경사항을 하나 이상의 "논리적 단위"로 묶는다. 좋은 단위는 "그 자체로 하나의 의미를 갖고, 되돌릴 때 통째로 되돌릴 수 있는" 덩어리다. 판단 기준:

- **같은 목적으로 묶는다.** 하나의 기능 추가, 하나의 버그 수정, 하나의 리팩터링에 관련된 파일들은 여러 개여도 한 단위다.
- **다른 목적은 분리한다.** 예를 들어 새 기능을 만들다가 발견한 무관한 버그를 같이 고쳤다면, 기능 추가와 버그 수정은 별개 단위로 나눈다. 포맷팅/린트성 변경이 기능 변경과 섞여 있다면 이것도 분리를 고려한다(단, diff가 너무 잘게 얽혀 있어 물리적으로 분리하기 어려우면 무리하게 나누지 않고 이유를 설명한다).
- **파일 하나에 여러 목적이 섞여 있는 경우**, git의 파일 단위 스테이징 특성상 완벽히 분리하기 어려울 수 있다. 이럴 때는 그 파일이 속할 가장 주된 단위를 정하고, 커밋 메시지에서 왜 그렇게 묶었는지 밝힌다.
- 단위가 하나뿐이면(변경사항 전체가 하나의 목적) 그대로 커밋 하나로 진행한다 — 억지로 쪼개지 않는다.

## Step 3: 커밋 메시지 작성

각 단위마다 아래 형식으로 메시지를 작성한다(저장소에 다른 컨벤션이 이미 있으면 그것을 우선한다):

```
<type>: <한국어 요약>
```

- `type`은 변경의 성격에 따라 고른다: `feat`(기능 추가), `fix`(버그 수정), `refactor`(동작 변화 없는 구조 개선), `chore`(빌드/설정/의존성 등 잡무), 필요하면 `docs`(문서), `test`(테스트), `style`(포맷팅), `perf`(성능)도 쓴다.
- 요약은 명령형보다는 담백한 서술형으로, 무엇을 왜 바꿨는지 한 줄로 드러나게 쓴다("~함", "~수정" 같은 간결한 종결 선호). diff에서 실제로 확인한 내용만 쓰고, 코드를 보지 않고 추측한 내용은 쓰지 않는다.
- 변경 이유나 배경이 코드만 봐서는 드러나지 않고 사용자와의 대화에서 나왔다면, 본문(제목 다음 빈 줄 + 설명)에 그 맥락을 짧게 덧붙인다. 자명한 내용(코드를 보면 바로 아는 것)은 본문에 반복하지 않는다.

## Step 4: 사용자 승인

커밋을 실행하기 전에, 계획한 단위와 메시지를 표로 제시한다:

```
커밋 계획

| # | 파일 | 메시지 |
|---|------|--------|
| 1 | src/foo.ts, src/foo.test.ts | feat: 사용자 검색 필터 기능 추가 |
| 2 | src/utils/date.ts | fix: 시간대 변환 시 자정 경계 오류 수정 |
```

사용자에게 다음을 확인받는다:
- **전체 승인**: 계획대로 전부 커밋
- **일부 수정**: 메시지 문구나 단위 분리를 수정해달라는 피드백 반영 후 다시 제시
- **선택 커밋**: 일부 단위만 커밋
- **취소**: 커밋하지 않고 종료

승인 없이 커밋을 실행하지 않는다.

## Step 5: 커밋 실행

승인된 단위마다:

1. 해당 단위에 속한 파일만 `git add <file1> <file2> ...`로 스테이징한다. `git add -A`나 `git add .`는 쓰지 않는다 — 승인받지 않은 다른 변경까지 같이 커밋되는 것을 막기 위함이다.
2. 커밋 메시지는 여러 줄(본문 포함)일 수 있으므로 heredoc으로 전달한다:
   ```
   git commit -m "$(cat <<'EOF'
   <type>: <요약>

   <본문(있으면)>
   EOF
   )"
   ```
3. 커밋 직후 `git log -1 --stat` 등으로 실제로 의도한 파일만 포함됐는지 확인한다.
4. 모든 단위를 순서대로 커밋한 뒤 `git status`로 남은 변경사항(이번에 커밋하지 않기로 한 것)을 안내한다.

커밋 훅(pre-commit)이 실패하면 원인을 파악해 고치고 다시 스테이징·커밋한다. `--no-verify`로 훅을 건너뛰지 않는다.

## 주의사항

- `.env`, 자격증명 파일, 키 등 시크릿으로 보이는 파일이 변경 목록에 있으면 커밋 계획에 포함하기 전에 사용자에게 알리고 정말 커밋할 의도인지 확인한다.
- push는 이 스킬의 범위가 아니다 — 커밋까지만 하고, push 여부는 사용자가 별도로 요청할 때만 진행한다.
- 기존 커밋을 `--amend`하지 않는다. 항상 새 커밋을 만든다(사용자가 명시적으로 amend를 요청한 경우는 예외).
