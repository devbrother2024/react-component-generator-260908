# TDD Rule

> ⚠️ **이 규칙은 Rigid(고정) — 상황에 맞게 변형하지 마라.** 예외가 필요하다고 느껴져도 아래 "적용 기준"과 "변명 차단표"를 먼저 확인하라.

## 0. 우선순위 조항

**이 파일은 기본값(fallback)이다.** 프로젝트 루트 또는 하위 디렉토리의 `CLAUDE.md`/`AGENTS.md`에 TDD 관련 규칙이 명시되어 있다면 **그 규칙이 이 파일보다 우선한다**. 충돌이 없는 범위에서만 이 파일을 함께 적용하라.

## 1. 적용 기준

### TDD를 **반드시** 적용해야 하는 대상
- **비즈니스 로직** (조건 분기, 계산, 상태 전이 등)
- **API 엔드포인트/핸들러** (요청-응답 계약이 있는 코드)
- **유틸리티 함수** (입출력이 명확한 순수/비순수 함수)
- **버그 수정** (회귀 방지를 위해 실패 재현 테스트가 선행되어야 함)

### TDD가 **불필요**한 대상
- **타입 정의** (`.d.ts`, interface/type만 있는 파일)
- **설정 파일** (`vite.config.ts`, `tsconfig.json`, `.eslintrc` 등)
- **순수 UI** (마크업/스타일만 있고 로직이 없는 프레젠테이셔널 컴포넌트)
- **SQL** (스키마/마이그레이션 정의 자체)

## 2. RED-GREEN-REFACTOR 사이클

### RED
- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 몰아넣지 마라.
- 테스트 작성 후 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않고 다음 단계로 넘어가는 것은 금지.
- 실패 이유는 **오직 "기능 미구현"**이어야 한다. 문법 오류, import 누락, 오타로 인한 실패는 무효 — 수정 후 다시 확인하라.

### GREEN
- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI 원칙**: 지금 테스트가 요구하지 않는 기능·분기·매개변수를 추가하지 마라.
- **신규 테스트 + 기존 테스트 전체**가 통과하는지 반드시 확인한다 (회귀 여부 체크).

### REFACTOR
- 중복 제거, 이름 개선, 헬퍼 추출 등 **구조 개선만** 수행한다.
- 전체 테스트가 **green을 유지**하는 상태에서만 리팩터링을 진행한다.
- 이 단계에서 **새로운 동작을 추가하는 것은 금지** — 새 동작이 필요하면 다음 RED로 넘어가라.

### 반복
REFACTOR가 끝나면 **다음 동작에 대한 RED로 돌아간다.** 사이클을 건너뛰지 마라.

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면**, 그 코드를 **삭제하고 RED부터 재시작**한다.
- "일단 참고용으로 남겨두기"도 **금지**. 순서를 어긴 코드는 예외 없이 삭제 대상이다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트 작성 비용이 낮다. 단순함은 테스트를 생략할 이유가 아니라 **가장 쉽게 작성할 수 있는 이유**다. |
| "나중에 추가하겠다" | "나중"은 오지 않는다. 테스트 없는 코드는 이미 회귀 위험을 안고 배포된다. 지금 RED부터 시작하라. |
| "시간이 없다" | 테스트 없이 디버깅하는 시간이 테스트 작성 시간보다 항상 길다. TDD는 속도를 늦추는 게 아니라 재작업을 없애는 것이다. |
| "삭제하면 낭비다" | 순서를 어기고 작성한 코드는 검증되지 않은 코드다. 낭비는 검증 없는 코드를 유지보수하는 것이지, 그것을 삭제하는 게 아니다. |
| "프로토타입이다" | 프로토타입은 프로덕션 코드로 승격되는 경우가 많다. "임시"라는 딱지는 규칙을 우회하는 핑계가 되어서는 안 된다. |
